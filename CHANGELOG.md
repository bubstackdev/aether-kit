# Changelog

All notable changes to AetherKit. Versions follow semantic versioning; 0.0.x releases are experimental previews with no API compatibility promise.

## Unreleased

### Package floor: macOS 14 / iOS 17

- **The package floor is now macOS 14 and iOS 17** (it was 27), so apps can link the language facade there, where it reports `.unsupportedOS`. **Core AI products still need macOS 27 or iOS 27 at runtime:** every declaration in `AetherCoreAI`, `AetherLanguageCoreAI`, `AetherH3CoreAI`, `AetherKreaCoreAI`, `AetherFlux2CoreAI`, `AetherSpeechCoreAI` and `aether-probe` is now `@available(macOS 27, iOS 27, *)`, so an app below 27 calls them behind `#available`; apps already at 27 change nothing. CoreAI and FoundationModels link weakly, with no linker flag, because every reference to them is availability-gated ([deployment floor](docs/deployment-floor.md)).
- **Tests need the 27 triple:** `swift test --triple arm64-apple-macosx27.0` (or `MACOSX_DEPLOYMENT_TARGET=27.0` under xcodebuild). `Scripts/check.sh`, `check-cpu.sh` and the Kokoro qualify and sweep scripts pass it; a bare `swift test` fails with `'RunTestsWithTheOS27Triple' is only available in macOS 27 or newer`.
- **AetherLanguage:** the OS is checked before the bundle, so below 27 `availability` is `.unsupportedOS` whatever the bundle holds (and `contextLength` is 0). A new CPU test covers that branch through an injected OS check.
- **AetherAssets:** `DeclaredModelAsset.verifyConcurrently` uses `OSAllocatedUnfairLock` instead of `Synchronization.Mutex`, which needs macOS 15 / iOS 18. Behaviour is unchanged.
- **Scripts:** `Scripts/annotate-floor.py` gates the Core AI targets and, with `--check`, fails CI on a declaration without the attribute. `Scripts/check-floor.sh` now builds every product at macOS 14 and every library at iOS 17 instead of typechecking two targets, and checks that `Examples/FloorConsumer` weak-links CoreAI. `Scripts/launch-floor-consumer.sh` launches that consumer on an older OS.
- **CI:** a new **Launch at the macOS 14 floor** job runs the floor consumer on a GitHub-hosted `macos-14` runner, which has no CoreAI, and requires `unsupportedOS`; it is part of **CI passed**.

### Added

- **Language resource admission:** `LanguageGenerationSession.open(bundle:…, resources:)` and `VisionLanguageSession.open(bundle:…, resources:)` take a `LanguageResourceAdmission`, which reserves each model's residency and each request's (and image encode's) scratch against a host's `ResourceCoordinator`, keyed by the registered model hashes, as Krea and FLUX.2 do. With `gpu:`, opening (each model's load and specialization) now waits for a GPU grant too. Prompted by a VL-4B plus Krea crash under memory pressure on 0.0.2; measured estimates and a cross-process protocol proposal are in the [design](docs/qwen3-vl-resource-admission.md).
- **Qwen3-VL coverage:** prompts with several images are qualified against upstream on the VL-2B and VL-4B (the plan's expansion and M-RoPE positions equal upstream's rope index for every token; native model parity and same-decode runs pass with identical greedy output), and EXIF-rotated photos give the unrotated photos' results exactly ([multi-image](docs/evidence/qwen3-vl-multi-image-2026-10-27.json), [4B](docs/evidence/qwen3-vl-multi-image-4b-2026-10-28.json), [rotated](docs/evidence/qwen3-vl-rotated-photos-2026-10-27.json)). `Forge/language/reference_qwen3_vl.py` takes several images per case and `--exif-transpose`.
- **Sampling on the image path:** `VisionLanguageSession` and the image `LanguageGenerationSession.generate` have a sampling entry point (`sampling:`, optional `constraint:`, returning `LanguageGenerationResult`) through the shared decode loop, so Qwen3-VL prompts take seeded random sampling, the repetition penalty and token constraints as text requests do. The greedy entry points are unchanged, token for token ([evidence](docs/evidence/qwen3-vl-sampling-2026-10-27.json)).
- **AetherLanguageRuntime:** a new backend-neutral library with no Core AI, Metal or AetherKit dependency, built at the macOS 14 / iOS 17 floor. It holds the `LanguageBackend` protocol, the seeded sampler (repetition penalty, temperature, top-k, top-p; matched against Transformers 4.57.3's processors), a token-constraint hook for constrained decoding, and the shared decode loop ([design](docs/language-runtime-seam.md)).
- **AetherLanguageCoreAI:** `LanguageGenerationSession` conforms to `LanguageBackend`. Greedy stays the default, and its output is token-identical to 0.0.2 on the qualified models. Sampling and constraints are opt-in per request ([guide](docs/language-generation.md)).
- **AetherLanguage** (experimental): the app-facing text facade in FoundationModels' shape. `AetherLanguageModel(bundle:)` takes an installed bundle and reports `availability` without hashing or loading (`unsupportedOS`, `unsupportedPlatform`, `bundleMissing`, `bundleInvalid`, `unsupportedTemplate`), then loads lazily, fully verified, on `prewarm()` or the first request. `AetherLanguageSession` has instructions, `respond(to:options:)`, `streamResponse(to:options:)` (cumulative snapshots with deltas, which never split a UTF-8 scalar or a grapheme cluster), and a Codable transcript; a turn is kept only when it completes. `AetherGenerationOptions` uses FoundationModels' names (`samplingMode`, `temperature`, `maximumResponseTokens`) plus `stopSequences`, `repetitionPenalty` and `reasoning`. Greedy is the default, and the output limit defaults to the remaining context capped at 4,096. Reasoning models return their thinking separately. The Core AI backend is chosen behind `#available(macOS 27, iOS 27, *)`. Natively, greedy replies equal the runtime's on the Qwen3-0.6B and the 4B writer ([design](docs/language-facade.md), [evidence](docs/evidence/language-facade-native-2026-10-27.json)).
- **AetherLanguageFoundationModels** (experimental, OS 27): `AetherLanguageModel` conforms to FoundationModels' `LanguageModel`, so an app keeps `LanguageModelSession` and passes `model: AetherLanguageModel(bundle:)`. FoundationModels' options and reasoning levels (any level turns thinking on) map onto the facade's. It declares reasoning when the bundle does, and not tool calling, attachments or guided generation (`@Generable` follows in the structured-output piece). Natively, `LanguageModelSession(model:)` returns the facade's replies.
- **Structured output** (experimental): `AetherLanguageSession.respond(to:generating:)` decodes a reply into an `AetherGenerable` type (`Decodable` plus a static `AetherGenerationSchema`), with generation constrained by a JSON-schema constraint that runs beside each decode step. The schema subset is what FoundationModels' `@Generable` emits; anything else (a regex `pattern`, for example) is refused, never run unconstrained. `AetherGenerationSchema` builds schemas for Swift types (`AetherGenerationGuide` mirrors `GenerationGuide`) or reads FoundationModels' `GenerationSchema` JSON. Natively, on the Qwen3-0.6B and the 4B writer, replies decode into nested types with arrays, enums and guides, greedy and sampled; the constraint averages under 0.1 ms per call ([design](docs/language-facade.md#structured-output), [evidence](docs/evidence/language-structured-output-2026-10-27.json)).
- **AetherLanguageMacros** (experimental): `@AetherGenerable` and `@AetherGuide`, which write a struct's or enum's schema (identical to FoundationModels' for the same declaration) and, for enums, its decoding. It's a separate product so apps that don't use it don't build swift-syntax.
- **AetherLanguageTokenizers:** `LanguageTokenBytes`, each token ID's raw bytes for byte-level BPE tokenizers (GPT-2 and Qwen families), from `LanguageTokenizer.tokenBytes(bundle:)` or `tokenBytes(directory:)`. On the four pinned Qwen3 and Qwen3-VL snapshots, the bytes of every chat-oracle prompt are exactly upstream's rendered text.
- **Examples/FloorConsumer:** a consumer package at macOS 14 / iOS 17 that links `AetherLanguage` and prints its availability; CI's launch subject.
- **AetherKit:** `LanguageModelManifest.locate(in:platform:)`, the registration's structural checks (schema, platform, bounds, and model and tokenizer paths inside the bundle that exist) without hashing anything.
- **Load/unload cycling:** `flux2UnloadCycling`, `kreaUnloadCycling` and `kokoroUnloadCycling` are opt-in native tests (`AETHER_NATIVE_UNLOAD_CYCLING=flux2|krea|kokoro`). Each opens a session, makes one small request and unloads, five times over, reading memory after each unload. The 0.4–0.7 GB that FLUX.2 and Krea leave after unload grows for three cycles and then stays flat. It is macOS malloc's cache of freed large blocks, not a Kit or Core AI leak: with `MallocLargeCache=0` both stay flat from the first cycle. Kokoro bucket 2048's footprint falls under 0.3 GB within 2 s of `unload()`, and the 8.1 GiB Metal counter that remains isn't held memory; 2048 stays opt-in. No library change ([FLUX.2](docs/flux2-klein.md#memory-after-unload-003), [Krea](docs/krea-generation.md#memory-after-unload-003), [Kokoro](docs/kokoro-speech.md#memory-after-unload-003), [evidence](docs/evidence/unload-cycling-2026-10-27.json)).
- **FLUX.2 encoder cancellation:** `flux2NativeEncoderCancellation`, an opt-in native test, cancels requests while the text encoder opens, loads and runs, and, with `AETHER_FLUX2_REFERENCE_FIXTURES`, while the reference-image encoder does. Core AI runs a submitted call to completion and can't interrupt a function load, so a cancel waits for the one in flight: about 0.17 s during the text encoder's call, up to about 0.9 s if it lands during a balanced session's function load (about 3.8 s on a process's first request), and about 0.18–0.21 s during a reference image's call. Kit then discards the encoder and throws `CancellationError`, no native call starts after the cancel, and the next request reproduces the uncancelled result exactly. No library change ([text encoder](docs/flux2-klein.md#text-encoder-cancellation-003), [reference encoder](docs/flux2-klein.md#reference-encoder-cancellation-003)).
- **FLUX.2 benchmark harness:** `aether-probe benchmark-flux2` and `Scripts/benchmark-flux2.sh prepare|run`, after the Krea harness, with two plans that pin the bundle and both fixtures (`Benchmarks/flux2-baseline.json` encodes the prompt and references every iteration; `flux2-provided.json` uses the fixture's text rows). Each case records per-stage timings and memory peaks and must reproduce its first iteration's pixels exactly. Its `--run` mode takes the shared GPU lease itself, as `benchmark-krea` does. `prepare` passes for both plans; the measured run waits for a quiet window ([guide](docs/flux2-klein.md#benchmark-harness-003), [GPU lease](docs/gpu-lease.md)).
- **FLUX.2 prompt adherence:** `flux2PromptAdherenceGenerate` and `flux2PromptAdherenceJudge` (opt-in) answer the plan's yes/no questions about each image with a local Qwen3-VL judge (`huihui-ai/Huihui-Qwen3-VL-4B-Instruct-abliterated`, a fine-tune of Qwen3-VL-4B-Instruct) and compare Kit against the float32 Diffusers reference on the same noise ([`Benchmarks/flux2-prompt-adherence.json`](Benchmarks/flux2-prompt-adherence.json)). Kit and the reference both score 38/38, Kit 114/114 over three extra seeds, and the judge answers all 50 controls no. That is the ceiling: the set shows no adherence loss but can't measure a small one ([guide](docs/flux2-klein.md#prompt-adherence-003), [evidence](docs/evidence/flux2-prompt-adherence-2026-10-27.json)).
- **iPhone hosts (prepared, not yet run on a device):** `Examples/LanguageDevice`, an app that checks a staged Qwen3 or Qwen3-VL bundle registered for iOS against the float32 reference, staged by `Forge/language/stage_device_assets.py` ([guide](docs/language-generation.md#on-device-host-prepared-003)). KokoroDeviceProbe gains a decoder-only mode for the float16 Neural Engine retest, and the Kokoro references gain a bucket-512 case, `medium-af_bella`, which passes native parity on the Mac; a first choice, `medium-am_adam`, was rejected and recorded ([guide](docs/kokoro-speech.md#iphone)).
- **MLX older-OS backend spike:** `Spikes/mlx-backend`, a separate package, runs the Qwen3-0.6B and the 4B writer through mlx-swift at macOS 14 and passes Kit's language qualification criteria. The verdict is a conditional go for a separate optional product; nothing under `Sources/` changes ([report](docs/spikes/mlx-backend-2026-10.md)).
- **Language time to first token:** `languageTimeToFirstToken`, an opt-in native test under the GPU lease, times one-token requests at several prompt lengths across raw assets (a bucketed and a running export of one checkpoint, and other prefill widths), split by native submission, and requires the greedy first tokens to agree ([guide](docs/language-generation.md#time-to-first-token), [evidence](docs/evidence/language-time-to-first-token-2026-10-27.json)).
- **Split-attention spike:** a no-go under the current Core AI. A separate prefill function wires a second copy of the weights, split attention in `main` halves decode, and a `torch.cond` between the two hangs the GPU compile. The defects are Core AI's, not Kit's; both have minimal repros as Apple Feedback candidates ([report](docs/spikes/split-attention-2026-10.md)).

### Changed

- **AetherLanguageCoreAI, long-prompt time to first token (behaviour change):** on text bundles and one-function Qwen3-VL bundles, a bucketed request now allocates its KV cache for the whole prompt before the prefill, and a prompt longer than 256 tokens prefills in 256-token chunks (64 below, as before). A 0.0.2 two-function Qwen3-VL bundle keeps the 0.0.2 plan for every request. Warm time to first token at 2,048 tokens falls from 365-371 to 147-155 ms on the Qwen3-0.6B and from 949-973 to 489-533 ms on the 4B writer, and about as much at 1,024. Prompts of up to 256 tokens keep the 0.0.2 plan (their parity runs reproduce the earlier minimum cosines exactly); on every qualified image prompt (449-539 tokens) replies are token-identical to before; the long text prompts pass upstream parity, with greedy flips against other plans only at upstream near-ties (margins 0.00142, 0.00574 and 0.00791). The plan check (`languageOverlappedPrefillMatchesOtherPlans`) now judges its step-back comparison by the same near-tie rule as its plan-rounding ones, with the two plans' rows at its last-row bar (cosine >= 0.9999); before, step-back allowed no divergence and the row bar was 0.99999, which the VL-4B's and the writer's flips missed although both pass upstream parity. Growing the cache in 256-row steps through the prefill had made every step a new input shape, on which Core AI retains memory: the writer retained 272 MiB per 2,044-token request, about four times the guide's 449-token figure, and now retains 139.5. Just above 256 tokens the wider chunk retains about twice as much (writer 449 tokens: 58.6 to 109.8 MiB, 3 memory-budget reloads in 60 requests instead of 1) ([guide](docs/language-generation.md#time-to-first-token), [evidence](docs/evidence/language-prefill-plan-2026-10-28.json)).
- **H3 timing reference:** a quiet-host reference on M5 Max at 960×544×124, Turbo8: T2VA about 358 s and FL2VA about 343 s of stage time, denoising 308 and 289 s ([guide](docs/h3-integration.md#quiet-host-timing-reference-2026-10-28)).
- **AetherVision alpha (behaviour change):** `VisionRGBImage` now drops alpha and keeps each pixel's stored colour by default, as Transformers' `load_image` (`convert("RGB")`) does, for parity with upstream preprocessing. Kit 0.0.2 composited transparent and semi-transparent pixels over opaque black (Core Graphics source-over in the image's own RGB colour space: stored colour times alpha), and `.composite(red: 0, green: 0, blue: 0)` keeps that, passed to `VisionRGBImage(contentsOf:alpha:)` or `VisionRGBImage(cgImage:alpha:)`. The new `VisionAlphaPolicy` chooses. Exact for straight-alpha 8- and 16-bit images (how ImageIO returns PNG); a source that arrives premultiplied has lost the stored colour of fully transparent pixels, which become black. Rotated files are now oriented by moving pixels after a full-size decode, byte-identical to ImageIO's oriented decode for opaque images ([evidence](docs/evidence/qwen3-vl-alpha-2026-10-27.json)).
- **AetherH3CoreAI (qualification):** `H3ProfileEngine.stages(..., nativeObserver:)` reports every native submission of every stage's graphs (`H3NativeCall`: role, call count, begin/end/failed). `aether-probe qualify-h3-session-lifecycle` uses it to qualify cancellation during each stage, unload during active work, and retained- and reopened-session recovery against the baseline's trajectory, frames and PCM; `Scripts/audit-h3-media.py` audits a render's frames and audio. `h3-memory-render`, `h3-memory-encoder` and the new command now take the GPU lease themselves.
- **H3 denoiser memory:** the body and heads graphs now see one modulation shape per render. Their `temb` inputs are dynamic in the step's timestep cardinality (T2VA 1 then 2, FL2VA 2 then 3), and Core AI keeps a specialization per shape until release, so step 1 left a second body specialization resident (about 2.5 GiB). `H3ModulationPadding` pads each step's AdaLN tables and embedding to the trajectory's largest cardinality by repeating rows; it is exact because the graphs select rows only by index. This is a workaround for Core AI's retention, not a fix. Steady denoising at 960×544 falls from 13.49 to 10.93 GiB on T2VA and from 13.80 to 11.17 GiB on FL2VA, the video-decode footprint from 11.07 to 8.16 GiB, step time is unchanged, and both qualified captures replay all 457 hashes. Measured admission does not fall: an unexplained step-0 transient, up to 16.12 GiB of Metal, appeared in 2 of 9 full-size padded renders (both gate renders). Whether padding causes it is unknown, because the unpadded build was never measured under the same busy-host gate conditions, so the entry covers it, for an admitted worst case of about 16.6 GiB, higher than the unpadded build's 15.26 GiB and under the 18 GiB bar ([guide](docs/h3-integration.md#denoiser-memory-one-modulation-shape-per-render-2026-10-27)).
- **Qwen3-VL decoder, one function:** `LanguageGenerationSession` accepts a bucketed `main` that takes image rows aligned with the tokens (`image_embeds` [q, hidden], `deepstack` [levels, q, hidden]) and sends text, image and decode steps through it, prefilling the whole prompt in the fixed-width chunks; `imagesThroughMain` reports it. Core AI wires a copy of the weights per function, so the 0.0.2 `main` + `withImage` pair kept two: the re-exported VL-4B wires 8.4 GiB instead of 16.1 GiB for an image request, its compiled cache is 15.0 GiB instead of 22.5 GiB, and both models pass every 0.0.2 parity gate again. An image request retains more memory than before (about 100 MiB on the 4B), so the memory budget reloads the 4B about twice as often. Two-function bundles keep working ([guide](docs/qwen3-vl.md#one-decoder-function-003), [design](docs/qwen3-vl-single-decoder.md)).
- **Qwen3-VL text export (Forge):** `export_qwen3_vl_text.py` writes the one-function contract and bounds its memory: an fp16 build, the eager reference first, and the self-check in a fresh process. The VL-4B export peaked at 16.3 GB RSS (0.0.2: 31.7 GB). The 0.0.2 peak came from about five copies of the weights at the self-check, not from one copy per exported program.
- **AetherFlux2:** the bundle fingerprint now also hashes `tokenizer/chat_template.jinja`, which renders the prompt. The template is required, checked against provenance and rechecked by `verifyTokenizer()`. The same qualified bundle bytes therefore have new identities: fingerprint `d27cefc4…` (was `a48aaf07…`) and reference fingerprint `d8a98cb0…` (was `a69abb8e…`). Anything an app keys on the old fingerprint (installation IDs included, which embed it) needs the new one. Native parity (113/113) and lifecycle (44/44) re-run under the new identities give check values identical to the 0.0.2 qualification ([guide](docs/flux2-klein.md#chat-template-in-the-fingerprint-003)).
- **AetherLanguageCoreAI:** `LanguageGenerationError` moves to `AetherLanguageRuntime`, which `AetherLanguageCoreAI` re-exports, so existing code compiles unchanged.
- **AetherKit:** `Synchronization.Mutex` (macOS 15, iOS 18) is replaced inside `GPUAdmission`, `SharedGPULease` and `ResourceCoordinator` by an internal unfair lock over `OSAllocatedUnfairLock` (macOS 13, iOS 16), so `AetherKit` builds at the facade's macOS 14 and iOS 17 floor. Behaviour is unchanged; the lease and admission tests pass as before.
- **AetherKit:** `LanguageModelManifest.verify(in:platform:)` runs `locate` first, so a bundle whose `main.mlirb` or `tokenizer.json` is missing now fails with `AetherError.invalidModel("language model or tokenizer file missing")` before any hashing, instead of the file-open error it threw before.
- **AetherLanguageFoundationModels:** `AetherLanguageModel` now declares guided generation, so FoundationModels' `@Generable` requests (`respond`/`streamResponse(generating:)`) run under the JSON-schema constraint; an unsupported guide throws `LanguageModelError.unsupportedGenerationGuide`.
- **AetherLanguage:** `AetherLanguageError` gains `unsupportedSchema` and `decodingFailure`; exhaustive switches over it need the two cases.
- **Dependencies:** swift-syntax, pinned exactly to 604.0.0 (the Swift 6.4 toolchain's), for the `AetherLanguageMacros` compiler plugin only; it runs on the build host and isn't linked into apps. The examples' `Package.resolved` files include it.
- **Scripts:** `Scripts/check-language-runtime-floor.sh` is renamed `Scripts/check-floor.sh`, which now checks the whole package at its floor (see Package floor above); CI runs it.
- **AetherFlux2Tokenizers:** `Flux2Tokenizer` renders prompts through the bundle's own chat template with `AetherLanguageTokenizers` (thinking off), with token IDs unchanged on every fixture prompt. The product now depends on `AetherLanguageTokenizers` instead of swift-transformers directly.
- **AetherCoreAI:** `SerialComputeStream` is now the only code that encodes to or joins a Core AI stream, for the H3 adapters, `LanguageGenerationSession` and `LanguageVisionEncoder`. That removes the 14 "sending 'stream'" warnings and the `@preconcurrency import CoreAI` lines. It is `@unchecked Sendable` on the invariant that each owner admits one submission at a time and joins it before the next. This is a workaround for Core AI's unannotated `ComputeStream`, not a fix, and goes once the SDK annotates it. Language chat replies and an H3 render's 457 boundary hashes are unchanged ([guide](docs/h3-integration.md#native-block-binding-checkpoint)).
- **FLUX.2 evidence:** native reports record both the text-to-image and the reference fixture IDs. The reference fixture is regenerated from the CPU text-to-image pictures: `80a86a51…` replaces `caf92bb7…`, and native parity passes 23/23 on the reference cases at unchanged bars. Inputs that don't depend on the pictures are byte-identical; the reference pixels and what is computed from them differ ([guide](docs/flux2-klein.md#independent-references)).
- **AetherLanguageCoreAI, bucketed prefill:** cache growth zeroes only each row's unwritten tail and copies rows in parallel, and a step's update rows are copied a row at a time instead of a token at a time. The bytes and replies are unchanged. At 2,048 tokens, bucketed TTFT falls from 554 to 496 ms on the Qwen3-0.6B and from 1,383 to 1,178 ms on the 4B writer (on a shared host, so partly noise). The running contract stays far faster for long prompts (83 ms on the 0.6B), because nearly all of the bucketed time is native per-submission cost ([guide](docs/language-generation.md#time-to-first-token)).

### Removed

- **AetherFlux2:** `Flux2Prompt.render(_:)`, the hand-written Qwen3 thinking-off render. Use `Flux2Tokenizer.prepare(_:)`, or `LanguageTokenizer.render([.user(text)], thinking: false)` on the bundle's tokenizer directory.

## 0.0.2 — 2026-10-27

Second experimental developer preview. See the [release notes](docs/release-notes/0.0.2.md).

### Added

- **AetherFlux2, AetherFlux2Tokenizers, AetherFlux2CoreAI** (experimental): FLUX.2 [klein] 4B text-to-image and multi-reference editing. Includes bundle validation with provenance and revision pins, portable installation, the empirical-shift schedule, 4-axis rotary tables, the padded Qwen3 prompt, reference-image policy and preparation, and `Flux2GenerationSession`. The session supports prepared prompts and references, balanced/resident residency, cancellation, terminal unload and optional resource admission. Native parity against independent float32 Diffusers references passes at 12 cases, and the native lifecycle suite passes 44/44 checks: cancellation, unload during work, resident reuse and admission ([guide](docs/flux2-klein.md)).
- **Shared:** `AetherKit.SeededGaussianNoise` (Krea noise delegates to it, with identical values), `AetherAssets.DeclaredModelAsset`/`BundleFiles`, and a package-internal staged-model admission decorator in `AetherCoreAI`.
- **AetherKit:**
  - `SharedGPULease`, a cross-process GPU lease wire-compatible with Atelier's `/tmp/atelier-gpu.lock` protocol. It provides fail-fast and waiting acquisition with timeouts, cancellation and busy reports (including pid-less leases). Release is owner-checked, idempotent and done by renaming the lease aside, so it never leaves a pid-less lease. It also provides signal release, `.reclaim`-serialized stale reclaim that never replaces a newer lease, and inheritance only on an explicit hand-off from a live ancestor (`AETHER_GPU_LEASE_HOLDER`).
  - `SharedGPULease.ToolPolicy`, which reads the `AETHER_GPU_LEASE`, `AETHER_GPU_LEASE_TIMEOUT` (bounded to one year), `AETHER_GPU_LEASE_PATH` and `AETHER_GPU_LEASE_HOLDER` overrides.
  - `GPUAdmission`, `GPUAdmissionOwner` and `GPUAdmissionGrant`: explicitly shared in-process admission that queues fairly or fails fast. The lease is an optional backend for unsandboxed hosts, with bounded turns between processes.
  - `FairInferenceQueue`, adopted from an earlier transport-independent admission design.
- **Sessions:** `KreaGenerationSession`, `Flux2GenerationSession`, `H3VideoSession` and `LanguageGenerationSession` accept an optional `gpu: GPUAdmissionOwner`. With it, operation reservations are taken after the grant and `unload()` withdraws an operation still waiting for the GPU. Sessions without it are unchanged.
- **AetherLanguageCoreAI:** `LanguageStepContract`, detected from the asset's function signature. The new `bucketedPositions` contract (`cache_positions`, host-written cache rows, last-row logits, fixed-width prefill chunks (power-of-two until the memory-budget change below), caches grown in 256-row steps) keeps input shapes in a bounded set, so it needs no shape recycling and its native shape cache stays bounded (one capacity per 256 tokens of context). A bounded shape set does not bound memory: Core AI still retains memory per request, and the memory budget below reloads it. It trades step cost for that: on Qwen3-0.6B fp16 a bucketed decode step measured 0.88× an unrecycled running step (0.84× at 8K), and time to first token was 2–3× longer with power-of-two chunks, while against default recycling it decodes 1.37–1.43× faster because no shape-recycling reloads occur ([evidence](docs/evidence/language-bucketed-decode-2026-10-26.json)). `runningPositions` (0.0.1) assets keep working unchanged. `CacheStatistics.distinctStepShapes` reports the submitted (q, capacity) pairs.
- **AetherLanguageCoreAI memory budget (a workaround for a Core AI bug):** Core AI keeps Metal allocations every time a reshape-enabled function changes input shape, until the model is released; every request changes shape (prefill chunks, then 1-token steps), so warm language requests kept growing memory (writer 137 MiB per 449-token request; Qwen3-VL-4B decoder 257 MiB). The bucketed contract was documented as bounded without reloads; that was wrong. Two changes bound it:
  - **Fixed prefill width.** The bucketed contract now prefills in one width C (default 64, `prefillChunkSize` overrides it) instead of power-of-two chunks, so a warm request switches only between q = C and q = 1. A run that is not a multiple of C ends with a C-token chunk stepping back over rows already written: the graph's cache mask admits only rows before the chunk's first position, so those rows are recomputed from the same prefix and overwritten. A run shorter than C is one chunk. On the writer, C = 64 retains 58.6 MiB per 449-token request (2.3× less than before) and reaches the first token in 0.21 s (0.28 s before); the C = 32/64/128/256 table is in the guide.
  - **Memory budget.** `LanguageGenerationSession` measures each request's Metal growth from GPU admission to its end. Once the growth retained since the model loaded passes `memoryGrowthBudgetBytes` (default `defaultMemoryGrowthBudgetBytes`, 2 GiB; nil disables; below `minimumMemoryGrowthBudgetBytes`, 256 MiB, refused), it reloads the model between requests: at idle, in the background under a GPU grant, right after the request that crossed the budget, or else in front of the next request under its grant. A request arriving mid-reload waits for it; `unload()` withdraws or cancels a pending reload and never waits behind the GPU queue. The KV state is Kit-owned and unaffected. First use of a function or shape is not counted, and neither are net decreases or outliers (other allocators in the process), with outliers set aside capped at the budget per load. `CacheStatistics` adds `idleMemoryReloads`, `requestMemoryReloads`, `retainedMemoryBytes`, `memoryGrowthBudgetBytes`, `foreignMemoryRequests` and `foreignMemoryBytes`; `VisionLanguageSession.open` takes the budget and `decoderStatistics()` reports it.
  - Qualified on all four models over 60 back-to-back requests at the 2 GiB default: Metal stays within the post-warm level plus the budget, each model reloads once (at idle, never in front of a request) and every reply is identical across the reload; upstream parity re-run at the fixed width ([guide](docs/language-generation.md#native-memory-retention)).

Opens a snapshot or export folder, or a registered bundle after the new `LanguageModelManifest.verifyTokenizer(in:)`; never downloads. Templates resolve like the swift-transformers loader and drop one trailing newline as upstream Jinja does. `LanguageModelManifest` gains an optional `tokenizerFiles` (every tokenizer file's SHA-256, as exporters record it); when present, the tokenizer directory must hold exactly those files, so a swapped chat template is refused. All 24 cases of an upstream-Transformers oracle match token for token (Qwen/Qwen3-0.6B, huihui-ai/Huihui-Qwen3-4B-Instruct-2507-abliterated, Qwen/Qwen3-VL-2B-Instruct and huihui-ai/Huihui-Qwen3-VL-4B-Instruct-abliterated; `Forge/language/reference_chat_tokens.py`), and Qwen3's thinking-off render is exactly FLUX.2's prompt, so `AetherFlux2Tokenizers` can delegate later ([guide](docs/language-generation.md#tokenizer-and-chat-template)).

### Changed

- **Qwen3-VL memory, attributed:** the VL-4B's 19–22 GiB is not a leak. The opt-in `visionLanguageMemoryByPhase` measures it by phase, with residency ([guide](docs/qwen3-vl.md#limits-and-follow-ups), [evidence](docs/evidence/qwen3-vl-memory-by-phase-2026-10-27.json)); removing the decoder duplication is 0.0.3 work.

Everything resolves from public sources. Re-runs reproduce recorded outputs byte for byte: the Qwen3-0.6B long reference's forced logits and the H3 FL2VA keyframe condition ([record](docs/evidence/forge-environment-2026-10-27.json)). Not covered: the 2026-10-18 H3 chain, backbone and denoising oracles, which load the superseded prototype's forge and are marked legacy.
- **H3 denoising:** a step's 50 blocks now chain on the device. Each block binds its predecessor's output in place, and only the last output is read back (every output when a denoiser observer is attached). Outputs are identical: all 457 trajectory hashes replay for T2VA and FL2VA, and paired renders end on the same latents. Denoising is 7% faster (median 350.7 → 326.3 s at 960×544, n = 2 each, busy host); the Metal peak rises about 0.2 GiB ([guide](docs/h3-integration.md#denoiser-speed-device-chained-blocks-2026-10-26)).

## 0.0.1 — 2026-10-26

First experimental developer preview. Qualified on one Apple M5 Max running macOS 27.0.1 with Xcode 27.1 / Swift 6.4. See the [release checklist](docs/release-0.0.1-checklist.md) for scope and remaining gates.

### Added

- **AetherKit:** owned float32/fp16/int32 tensors and typed errors, `GeneratedImage` with reference float32 scaling and PNG output, and `LanguageModelManifest` registration and integrity checks.

- **AetherCoreAI:** local Core AI model loading and introspection, and a stateless typed reference executor (`ModelSession`) with one-call admission, cancellation and awaited `unload()`. Native functions are resolved once per model session. Sessions can open from installed assets. `ResourceCoordinator` and `ModelResourceAdmission` provide optional transactional reservations.

  - rotary inputs, the flow schedule and seeded noise
  - acceptance of the vanilla Krea 2 Turbo export
- **AetherKreaTokenizers:** a local Hugging Face tokenizer adapter that never downloads files.
- **AetherKreaCoreAI:**
  - `KreaGenerationSession` for text-to-image, reference images (vision encoder) and refine
  - balanced and resident residency, prepared prompts for encode-once rendering
  - cancellation and terminal unload
  - installed-asset sessions and `KreaResourceAdmission`

  - `LanguageGenerationSession` with a growable fp16 KV cache, chunked prefill and greedy decoding

  - H3 qualification and profile commands

### Performance

- Model-stream verification drains each read chunk and hashes Krea streams concurrently, keeping memory bounded and taking `verify-krea` from about 7 s to about 3 s.
- Contiguous native tensor outputs are copied in bulk, with validation.
- Language token delivery overlaps the next decode step.
