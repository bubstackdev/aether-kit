# AetherKit 0.0.7 — experimental developer preview

Released 2026-11-04.

0.0.7 is a small H3 release for Atelier:
- **H3 square canvas 704×704** (#96). A square keyframe no longer has to be cropped to 16:9 or 9:16: the 704² overlay
  on the 0.0.5 stack adds the square vision-tower graph and first-frame encoder tail, qualified natively and measured
  for 5 s and 10 s clips.
- **Canvas-scoped measured identity** (#96). A profile that only adds canvases keeps every measured entry it already
  had, so the square overlay didn't orphan the twelve 0.0.5 entries.

The frozen API ([API stability](../api-stability.md)) is unchanged: everything new is in `AetherH3`, which isn't
frozen, so the committed baseline in `api/` is still the 0.0.4 baseline, and the **Public API (frozen)** check passes
against it. **Outside the frozen API there is still no compatibility promise in 0.0.x**, and 0.0.7 has two H3
behaviour changes ([below](#source-changes-and-migration)).

## Install

```swift
.package(url: "https://github.com/bubstackdev/aether-kit", exact: "0.0.7")
```

Building needs Xcode 27.2 (Swift 6.4). See the [README](../../README.md) for the quick starts and the
[H3 guide](../h3-integration.md#square-canvas-704704-and-canvas-scoped-identity-007) for the square canvas.

## Highlights

- **Square canvas 704×704.** 704² is 22×22 latents, so a 10 s clip (243 frames) is 34,848 video rows, inside the
  40,960-row limit; 768² wouldn't fit 10 s. Only two graphs are new, each byte-identical to upstream on CPU: the
  704² vision tower and the first-frame encoder tail. Everything else is the 0.0.5 stack's. Qualified on the M5 Max:
  - **Tower:** within 0.69–0.90× upstream's own bf16 spread (bar 1.05×).
  - **Trajectory**, FL2VA 704² × 22, step 0: passes the 2% bar (block 49 1.57%), and every boundary hash replays.
  - **Quality:** a first+last render keeps 35.5 dB to each keyframe and moves to the last one (11.8 dB from the
    first), and the media audit passes.
  - **Memory**, six bundled entries:

    | Recipe | Task | 124 frames (18 GiB bar) | 243 frames (24 GiB bar) |
    | --- | --- | ---: | ---: |
    | Turbo8 | T2VA | 12.11 GiB | 19.81 GiB |
    | Turbo8 | FL2VA (first, last or both) | 12.95 GiB | 22.25 GiB |
    | Turbo4 | FL2VA (first, last or both) | 12.94 GiB | **23.54 GiB** |

    Turbo4 704² × 243 has only **0.46 GiB of headroom** under its bar. Turbo4 has no square T2VA entry. 24 GiB
    entries need a 64 GiB Mac.
- **Canvas-scoped identity.** `H3Profile.contentSHA256` fingerprints the whole profile, so adding any canvas changed
  every entry's key. `scopedContentSHA256(canvases:)` is the same fingerprint with the canvas-keyed graphs cut down
  to an entry's own canvases. A scoped entry (`identity_scope: canvases`, `h3.profile/3:…`) matches a profile only
  through its scope and covers only the canvases it lists. The twelve 0.0.5 entries are re-keyed with their numbers
  unchanged, and a 960×544 spot check on the square overlay is within them.

## Source changes and migration

0.0.7 changes no frozen API. These H3 changes affect code outside it:
- **Lookup change.** `H3MeasuredResources.entries`, `bundledEntries`, `bundledAdmission`, `entry(...)` and
  `bundled(executionIdentity:scopedIdentity:deviceArchitecture:)` take a `scopedIdentity` closure. Without it, a
  lookup that finds only canvas-scoped entries for the device throws `AetherError.invalidRequest` naming
  `scopedIdentity`, where it used to find nothing. On such a device, an identity that was never measured also gets
  `invalidRequest` rather than `unsupported`. **Migration:** pass `H3ProfileEngine.scopedResourceIdentity`.
  `H3ProfileEngine.measuredAdmission` already does, and is unaffected.
- **Coverage change.** A scoped entry covers only its listed canvases. 960×544 at 125–141 frames is no longer under
  the 1280×704 × 141 entries, and 288×288 is no longer under 960×544's.

[source changes and migration](#source-changes-and-migration). Everything outside the frozen API may still change in
any 0.0.x release.
