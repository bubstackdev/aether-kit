# AetherKit 0.0.6 — experimental developer preview

Released 2026-11-03.

0.0.6 is a small H3 release for Atelier:
- **Typed H3 limit refusals.** A request past one of H3's length limits is refused with `H3LimitExceeded`, carrying
  the limit and the request's numbers, instead of an `AetherError` whose message callers had to parse (#94). Its row
  case tells a size or length that fits no prompt from a prompt that pushes a clip over.

The frozen API ([API stability](../api-stability.md)) is unchanged: `H3LimitExceeded` is in `AetherH3`, which isn't
frozen, so the committed baseline in `api/` is still the 0.0.4 baseline, and the **Public API (frozen)** check passes
against it. **Outside the frozen API there is still no compatibility promise in 0.0.x**, and 0.0.6 has an H3 source
change ([below](#source-changes-and-migration)).

## Install

```swift
.package(url: "https://github.com/bubstackdev/aether-kit", exact: "0.0.6")
```

Building needs Xcode 27.2 (Swift 6.4). See the [README](../../README.md) for the quick starts and the
[H3 guide](../h3-integration.md#fl2va-conditioner-presentation-005) for the limits.

## Highlights

- **Typed H3 limit refusals** (#94). `H3LimitExceeded` is a public `Error`, `Sendable`, `Equatable` and
  `CustomStringConvertible`, and `@nonexhaustive`, so a `switch` over it needs `@unknown default`. Its cases:

  | Case | Thrown by | Payload |
  | --- | --- | --- |
  | `promptBytes(limit:bytes:)` | `H3ResourceAdmission.envelope(for:)`, so `H3VideoSession.generate` | The admission's `maximumPromptUTF8Bytes` and the prompt's UTF-8 bytes |
  | `presentationTokens(limit:prompt:keyframes:)` | The profile conditioner's preflight and encode, so `H3VideoSession.generate` before any stage | The profile's text-token limits (`ClosedRange<Int>`), the prompt's tokens, and the tokens the keyframes' labels and vision blocks add (0 for T2VA) |
  | `packedRows(limit:clip:prompt:)` | The profile conditioner's preflight, so `H3VideoSession.generate` before any stage | The denoiser's row limits (`ClosedRange<Int>`), the rows the clip needs without the prompt (target video, audio, the keyframes' condition video and presentation), and the prompt's tokens |

  The split answers the question callers had to guess at: **a size or length that fits no prompt** (`clip >=
  limit.upperBound`, since a prompt has at least one token), such as 1280×704 × 141 first+last, against **a prompt
  that pushes a clip over** (a shorter prompt fits). Likewise, a `presentationTokens` refusal whose `keyframes` alone
  exceed the limit fits no prompt. The messages are kept, and the bytes and rows messages now give the request's own
  numbers and how the rows split, but callers switch on the case. Other refusals (no measured entry, a canvas without
  a tower graph, a profile without the vision overlay or an audio decoder) stay `AetherError`.

## Source changes and migration

0.0.6 changes no frozen API. This H3 change affects code outside it:
- **The three length refusals are `H3LimitExceeded`.** They were `AetherError.invalidRequest` (prompt bytes,
  presentation tokens) and `AetherError.unsupported` (packed rows). **Migration:** catch `H3LimitExceeded` before
  `AetherError`, and drop any matching of their text ("H3 prompt exceeds", "H3 presentation has", "H3 clip needs …
  packed rows").

## Compatibility

The app-facing API frozen in 0.0.4 is unchanged ([API stability](../api-stability.md)). Coming from 0.0.5, see
[source changes and migration](#source-changes-and-migration): code that caught H3's length refusals as `AetherError`
catches `H3LimitExceeded`. Everything outside the frozen API may still change in any 0.0.x release.
