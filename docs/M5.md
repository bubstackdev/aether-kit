## Scope

**What a decision tower is here.** A model that answers *typed questions* about a *state* with a probability
distribution read from one forward pass, with nothing generated. The questions are `choice` (pick one of n options),
`score` (a level on an ordered scale) and `noul` (yes or no). DESIGN §9 and MANIFEST §1.4 give four shapes:

| Shape | Driver | How the answer is read | Surveyed bundles |
|---|---|---|---|
| LM readout | `decision-lm@1` | the decoder's logits at an answer slot, gathered at the option labels' ids (or a slot head, or a scalar per option row) | decider-0.8b, qwen3.5-2b-decision, openthai-systemone, apus-decision-v1-4b, system-one-scorer-4b; decider-2b-vision with its `vision` graph |
| Hidden state + host head | `decision-hidden-head@1` | hidden rows at marker positions, through a named host reducer (`pointerHead`, `optionRows`) over `tables` | kev-0.8b, kev-4b, d1-3b |
| Joint head | `decision-joint-head@1` | a hidden-only decoder, then a bucketed head graph over every question at once | clef-flash |
| Encoder | `encoder-decider@1` | one bidirectional pass, logits at the option marker positions | laya-multilingual, d1-omni-600m |

A *vision* decision tower is one of these with a `vision` graph (graph kind `vision-tower@1`) in front of it, its
image rows injected into the decoder as in a VLM. That is the M4g work, reused.

**In M5 (the exit criterion):** the value types, the `Decider` protocol and `LMReadoutDecider` (DESIGN §9), on
`decision-lm@1`, with one model of our own Forge export gated against recorded distributions.

It has the richest fixture: the author's 44 rows plus 13 requests, `api_assembly` (coreai-kit `SystemOneDeciderSmokeTests`). **Its license isn't in any file read** (open question 1). |

## The readout (`LMReadoutDecider`)

DESIGN §9's three steps, made concrete:

1. **Render.** The manifest's `decision.promptFormat` picks a `PromptFormat`. It turns `(state, question)` into
   **rows**: token ids split into a *state prefix* (shared by every question on the state, when `decision.state` is
   `sharedPrefix`) and a *question suffix*. Each row carries its slot positions (usually one, the last token) and,
   per slot, the label ids to gather. The format also says how a question becomes rows:
   - `decider`: a choice or a noul is one row, and a score is one yes/no row per level, with the levels' P(yes)
     normalized;
   - `decisionFunction` and `slot`: a score is one row over its levels.
2. **Feed.** Under one GPU grant for the whole `decide` call (below):
   - feed the state prefix once;
   - record a restore point: `snapshot()` when `hasRecurrentState`, else the position, for `rewind(to:)`;
   - for each row: restore, `prefill(suffix, logits: .last)`, and keep the slot row.

   With `decision.state: freshPerRow` (qwen3.5-2b-decision, per its README), every row starts from `reset()`.
   Multi-slot rows (decider-2b-vision: one slot per question in one row) need logits at chosen positions. On an S=1
   graph each `step` returns them anyway. Otherwise this needs a `LogitsSelection` case naming positions
   (**guess**: the decider-2b-vision slice decides between the two).
3. **Read.**
   - **Gather and normalize.** By the logits `space`:
     - `vocab`: gather the label ids;
     - `slots`: mask the slots past k to −∞, take the softmax over all of them, renormalize the first k and report
       the last slot as abstain;
     - `scalar`: one row per option, with the softmax across rows.

     Then apply `softmax(logit / T)`.
   - **Temperature.** T comes from the precedence MANIFEST §2.2 fixes: app (`DecisionRequest.temperature`) >
     catalog > manifest `calibration` (`byType`, `byTypeAndOptionCount` with the `choice:2` / `choice:3-5` buckets)
     > the format's default (1.03 for `decider`, its card's; else 1).
   - **What stays out of the answer.** A temperature never changes the argmax. Hashes, timings and the raw logits
     stay behind `@_spi(Diagnostics)` (DESIGN §11), not in the public answer as coreai-kit's `Readout` had them.

**Formats are values, selected by manifest, never by name.** `PromptFormats.make(manifest.decision, tokenizer:)` is a
small registry keyed by `promptFormat`. An unimplemented format fails at load as `unsupported`, before any GPU work.
This replaces coreai-kit's `contains("decider")`, which matched on directory names, and its 9-case switch repeated in
about 6 places. The label table (A–Z, then the two-letter single-token names up to 255, coreai-kit's
`LabelTable.decider`) is resolved to ids **at export** and written as `decision.labels.ids` (MANIFEST §2.7: "label
ids are resolved by the adapter from vocab and written as ids"). The driver checks that every id decodes to its
label.

**JSON states.** `State.json` must keep key order and render as the author's Python does (`json.dumps` separators,
`ensure_ascii`, `repr(float)`) for the prompt to be token-exact. AetherCore's `JSONValue.object` is an unordered
`[String: JSONValue]`. So M5a adds the ordered value and the Python-compatible formatter DESIGN §9 names `PyCompat`
(AetherCore). They're one shared primitive, never one per format (coreai-kit had 5 ordered-JSON copies and 4
`repr(float)` emulators).

## Drivers and blocks to add

Each model slice is a Forge exporter (with its CPU reference and gate) plus a driver: a `DriverContract`, the typed
fields of `decision` it reads, and a loaded value in `Registry.decide` (new, like `Registry.vision`).

| Driver | Contract (MANIFEST §1.4) | `decision` fields typed in its slice | Runs on |
|---|---|---|---|
| `decision-lm@1` | `decoder-lm@1`'s roles; `outputs.logits.space` required; a `decision` block; optional `image` block, `vision` graph, `prefill` function | `labels {rule, ids}`, `slot {rule: lastToken\|answerTokenId\|tokenPattern, …}`, `state: sharedPrefix\|freshPerRow`, `nSlots`, `abstainSlot`, `rowPerOption`, `multiSlotRows`, `noulOrder` | `DecoderEngine` through `any LanguageEngine` |
| `encoder-decider@1` (optional) | `encoder` in `tokens`, `attentionMask`, `questionType`; out `markerLogits`; optional function `act`; sequence `buckets` | `readoutMarkers`, `questionTypeOrder`, `noulOrder` | `StatelessPipeline` |
| `decision-hidden-head@1` (optional) | static-chunk `decoder` (out `hidden` [1,S,H], no logits); `states.sequence`; `limits.padTokenId`; `decision.head {reducer, tables, temperature?}` | `head` | `DecoderEngine` with a hidden output (below) |

**Engine additions:**
- **`hidden(at:)` (only with the kev slice; not needed for the exit criterion).** The survey settles its shape: the
  hidden-only graphs (kev S=128, d1-3b and clef S=64) return hidden at *every* position of a static chunk and have no
  logits. So `hidden(at:)` is a **host gather over the per-chunk output**, not a graph feature (survey question 29).
  Proposed: an optional refinement protocol `HiddenStateEngine: LanguageEngine` with
  `prefill(_:hidden: [Int]) -> HiddenRows`, which `DecoderEngine` conforms to when its graph binds `hidden`. Feeding is
  in static chunks, padded with `padTokenId` and the pad rows dropped (MANIFEST §3: "static chunk with padding").
  **Guess:** whether `DecoderEngine` takes a hidden-only graph through `decoder-lm@1`'s code path with the logits
  role relaxed, or needs a sibling configuration. It's decided in that slice.
- **A `prefill` function for our Qwen3.5 exports (`functions: {step, prefill}`, pf64, sharing the four states).**
  DESIGN §15 names this as the fix for decode-only hybrids. The zoo decider prefills one token at a time: coreai-kit
  measured 11–14 s for its 255-option row (1,965 tokens) and 186 ms per later question on a checkpointed state.
  `DecoderEngine` already schedules static-S prefill phases (§6.2). M5b exports `step` first and adds `prefill` if it
  gates, else in a follow-up slice.

## Public API sketch

The style follows AetherImage, AetherVision and ChatSession:
- one actor per loaded model, which serializes requests (they queue, never fail);
- `load(bundle:manifest:device:…)` plus `Registry.decide`;
- typed `AetherError`s;
- cancellation between rows.

```swift
// AetherDecide
public enum Decision {
    public struct Option: Sendable, Hashable { var id: String; var description: String }
    public struct Question: Sendable, Hashable {
        public enum Kind: Sendable, Hashable { case choice([Option]); case score(levels: [String]); case noul(yes: String?, no: String?) }
        var instructions: String; var kind: Kind
        static func choice(_ instructions: String, _ options: [String]) -> Question     // + score, noul
    }
    public enum State: Sendable { case text(String); case json(OrderedJSON); case image(ImageInput) }  // .audio with an audio decider
    public struct Answer: Sendable, Hashable {
        var ids: [String]; var probabilities: [Double]        // in the asked order
        var abstain: Double?                                  // slot heads only
        var best: String { get }; var confidence: Double { get }; var certainty: Double { get }  // 1 − normalized entropy
        var expectedLevel: Double? { get }                    // score
        var pYes: Double? { get }                             // noul
    }
}

public struct DeciderCapabilities: Sendable, Hashable {
    public struct Inputs: OptionSet, Sendable { static let images, audio }  // text and JSON always
    var inputs: Inputs; var maxOptions: Int
}

public protocol Decider: Actor {
    nonisolated var capabilities: DeciderCapabilities { get }
    func decide(_ state: Decision.State, _ questions: [Decision.Question], _ request: DecisionRequest) async throws -> [Decision.Answer]
}
public struct DecisionRequest: Sendable { var temperature: Double?  /* app override, every type */; var job: GPUJob? }

public actor LMReadoutDecider: Decider {
    init(engine: any LanguageEngine, tokenizer: TokenizerAdapter, manifest: Manifest, gpu: GPUAdmissionOwner = GPUAdmission.shared.owner("decide"))
    static func load(bundle: InstalledBundle, manifest: Manifest, device: Device,
                     engine: DecoderEngine.Options = .init(), gpu: GPUAdmissionOwner = …) async throws -> LMReadoutDecider
    func render(_ state: Decision.State, _ question: Decision.Question) throws -> [DecisionRow]  // token ids, for parity gates
}
```

- **`Decider` departs from DESIGN §9 in one detail.** §9 makes `capabilities` an OptionSet that includes
  `maxOptions`, but a count can't be a flag. Here it's a struct with an OptionSet of inputs.
- **`LMReadoutDecider` sits on the text stack's loading shape.** It takes `DecoderEngine.Options` and a
  `GPUAdmissionOwner`, like `ChatSession.load`, because it's a client of the engine, as the `Generator` is. KV
  capacity derives from the memory budget at load. `PipelineOptions` and `StatelessPipeline` are for the stateless
  deciders (`encoder-decider@1`) and for the vision tower in front of a decoder, as in M4g.
- **GPU admission.** There is one grant per `decide` call, at `request.job` priority (`.medium` without one). It's
  taken before the decider's own `SerialGate` turn, so priority orders one decider's requests too, and it's held from
  the state's prefill through the last row (DESIGN §10: "one grant is one turn"). Cancelling the task between rows
  leaves the engine at a restore point. The decider owns its engine: it isn't shared with a `ChatSession`.
- **Content filters.** Shieldstral stays M4j's `YesNoClassifier` in AetherEmbeddings, an example `ContentFilter`
  backend with no built-in policy. AetherDecide can't import AetherImage or AetherEmbeddings (DESIGN §3), so a
  `ContentFilter` built on any `Decider` is app code. If one is wanted, it belongs in an example. The kit ships no
  decision policy.

## Validation

- **A reference per model.** A Forge reference script runs the upstream PyTorch model on the CPU in float32 over **the
  same token ids** the Swift side renders. Rendering and the graph are gated separately, as M4 does with preprocessing.
  The script records, per fixture row:
  - the ids;
  - the slot positions;
  - the label logits;
  - the distribution at the format's temperature.

  The author's fixture (zoo `models/decider-0.8b/fixtures-decider-0.8b.json`: 44 rows and 13 `api_assembly`
  requests; not present locally) is a cross-check. So are coreai-kit's measured numbers.
- **Bars:**

  | Check | Bar |
  |---|---|
  | Prompt rendering | token ids exact against the reference's (and the author's builder) on every fixture row; slot positions exact |
  | Label ids | every `decision.labels.ids` entry decodes to its label |
  | Distribution | same argmax on every row; every option's probability within **0.02** of the CPU float32 reference (the decider card's ship bar; coreai-kit measured 0.0084 on the zoo's int8) |
  | Score | expected level within Σ level · \|Δp\|, as above; per-level P(yes) within 0.02 |
  | Engine | the shared-prefix readout equals the fresh-per-row readout bit for bit (snapshot/restore on the hybrid); `LanguageEngineInvariants` pass on the export |

  These are starting bars: confirm or tighten each from the first measurement, and never loosen one to pass. Our
  export is expected to be fp16 rather than the zoo's int8 (open question 2), so a much tighter bar is likely.
- **Hermetic tests:**
  - rendering known answers per format, from Python-recorded ids with the tokenizer files as a test fixture;
  - `PyCompat` against `json.dumps` and `repr` outputs;
  - label tables, calibration precedence and buckets, the slot masks and abstain;
  - the score-as-rows reduction;
  - on the fake decoder (DESIGN §12): `LMReadoutDecider`'s prefix reuse (rewind on an attention fake, snapshot on a
    recurrent fake), cancellation between rows, and the GPU grant's scope.
- **iPhone:** extend `Tools/DeviceGate` with each export that has an iOS variant. decider-0.8b ran on an iPhone 17 Pro
  in coreai-kit.

## Owner decisions this plan follows

1. Every model is our own Forge export with a CPU reference and a GPU gate, hosted under `aether-models` and pinned in
   the catalog.
2. Gemma-terms models are gated with automatic approval. None is in M5's scope.
3. Shieldstral is an example `ContentFilter` backend with no built-in policy. M5 adds no policy and no decider over
   it.
4. VLMs (M4g–h) come before M5. The vision decision tower (M5f) reuses their tower and injection work.
5. MLX has its own track. M5 only keeps `any LanguageEngine` at the seam.
6. GPU work goes through `GPUAdmission` with `GPUJob` priority.
7. Pipelines use the shared `PipelineOptions` and `StatelessPipeline`. The engine-backed decider follows
   `ChatSession`'s loading shape (above).
